## Why it belongs to FAPD even though the scan called it "informational"

Web Bot Auth lets a website **receiving** automated requests verify who
sent them: the bot signs each HTTP request, and publishes its public keys
in a directory at `/.well-known/http-message-signatures-directory` on its
own domain. Cloudflare's methodology post: *"If your site just serves
content, and doesn't make requests to other sites, you don't need it."*
FAPD's other half is a crawler that makes thousands of requests a day to
federal servers, and eleven agency sites currently refuse it at their web
application firewalls (registry `unavailable` entries). A cryptographic
identity is what the planned M-23-22 letters to those agencies were
waiting for (`docs/pre-publication-todo.md` launch item 3; ops backlog
**OB-3**).

## Scope (to be planned)

1. **GUIDE §4 amendment first** (respectful access): request signing as
   part of honest identification; the key's lifecycle; what we promise
   agencies.
2. **Keys:** Ed25519, generated by the operator, private key in the box's
   `secrets/` (read-only mount, `0600`, logged in the private secrets
   log). Rotation schedule and overlap window defined.
3. **Signing (Acquisition, `src/fapd/client.py`):** `Signature-Input`,
   `Signature` and `Signature-Agent` on every request per the current
   IETF webbotauth drafts (HTTP Message Signatures, RFC 9421, plus the
   Web Bot Auth architecture and directory drafts: **read the current
   revisions at plan time**). The key never appears in the fetch log
   (`HttpClient` already redacts credentials). A seam for the signer
   (code-standards §1 table row). Tests with a fixed key and a fixed
   clock.
4. **Directory (Publication or Operations):** the JWKS at
   `https://fapd.info/.well-known/http-message-signatures-directory` with
   the media type the draft requires. **Check whether the directory
   response must itself be signed.** If it must, a static file isn't
   enough, and the plan must choose between a build-time signed response
   with a short validity (regenerated by the backend, served with headers
   from an nginx `include` written at build) and another mechanism. Don't
   assume.
5. **Registration:** Cloudflare verified bots or signed-agents
   application, plus any other WAF vendor programs the blocked agencies
   use; outcomes recorded in registry notes (refusals are accountability
   data).
6. **Docs:** `docs/site/bot.md` (it already says "Planned: Web Bot Auth
   request signing"), agents.html crawler section, SERVER-GUIDE, secrets
   log; close OB-3 and the todo item in the same commit.

## Constraints carried forward

- Signing never changes request volume, pacing or budgets (GUIDE §4;
  CLAUDE.md §13: never loosen or evade to fix a symptom).
- A refusal after signing is still a refusal. It's recorded, and never
  worked around.
- The phase-7 plan follows the master plan's §7 working protocol:
  progress logs, WORKLOG, blog notes.
